# 재구축 아키텍처 기준

## 핵심 원칙
- 기존 구현을 그대로 복사하지 않는다. 원본 매뉴얼과 카드 자료를 증거 자료로 삼는다.
- 카드 원문/출처 데이터와 실행 가능한 규칙 명세를 분리한다.
- 알 수 없는 값은 0이나 무료로 치환하지 않는다.
- 데이터 검증, 규칙 단위 테스트, Android 빌드, 에뮬레이터, 실제 플레이를 각각 별도 상태로 관리한다.
- CI는 기본 검사 1개로 단순화하고, 무거운 데이터 감사 및 기기 검증은 명시적으로 실행한다.

## 모듈 경계 (초기 설계)
1. `data/source`: 원본 카드 JSON 및 출처 메타데이터. 대용량 카드팩은 별도 배포 팩으로 관리.
2. `data/derived`: 카드 ID에 연결된 검증 결과. 원본 파일을 덮어쓰지 않는다.
3. `src/card-data`: 스키마, 파싱, 정규화, 데이터팩 검증.
4. `src/rules`: 매뉴얼에 근거한 순수 규칙 함수. UI/Android에 의존하지 않는다.
5. `src/game`: 상태 전이와 게임 흐름. 규칙 모듈을 호출한다.
6. `app`: Android 컨테이너와 UI. 규칙 로직을 복제하지 않는다.
7. `tests`: 데이터·규칙·상태 전이 회귀 테스트.

## 신뢰 단계
- `source-missing`: 출처 값 없음
- `extracted-unverified`: 기계 추출, 미검증
- `image-candidate`: 이미지 분석 후보
- `image-verified`: 이미지와 대조 확인
- `manually-verified`: 수동 확인 완료

이 단계는 비용/규칙별로 기록하며, 단계가 없는 값은 확정값으로 취급하지 않는다.

## 진행 순서
1. 카드 데이터 무결성/필드 의미를 고정한다.
2. LP 및 소울 지불의 원자적 규칙 테스트를 만든다.
3. 게임 상태 전이를 구성한다.
4. 카드 효과 명세와 실행기를 유형별로 추가한다.
5. Android UI와 APK 빌드를 연결한다.
6. 에뮬레이터 및 실기기 플레이를 별도 검증한다.
