## 1. 최종 목표

이 프로젝트의 목표는 FM1 카드게임 카드 DB를 단순 수집·변환하는 것이 아니라, **15,350장 전체의 원본 데이터 완전성, 정합성, 의미 해석, 게임 규칙 연결까지 추적 가능한 데이터베이스를 만드는 것**이다.

최종적으로 다음을 만족해야 한다.

1. 카드 ID 기준 15,350장 전부 보존, 중복·누락 0.
2. 원본 55개 필드의 카드별 값을 보존하고 존재/빈값/비적용/미확인/해석 상태를 구분.
3. 원본 카드 텍스트, 상세 URL, 이미지와 체크섬을 보존.
4. `RequireLP`, `RequireSoul`, `Skill1`, `Skill2`, `TextBase`, `TextExtra`를 출처·검증상태가 있는 구조화 데이터로 연결.
5. 48,281개 효과 절 전체에 해석 레코드를 연결하고 실제 효과, 조건, 기술/카드 참조, 메타데이터, 플레이버 문구를 분리.
6. 비용 토큰 파싱 성공과 실제 게임 내 지불 규칙 검증을 분리. 하이브리드/NCS/BONUS 토큰을 임의로 일반 색상으로 치환하지 않음.
7. 스킬은 이름 연결을 넘어서 정의, 조건, 대상, 효과, 발동 시점과 엔진 검증까지 연결.
8. SQLite 무결성, 외래키, 카드-이미지-효과-기술-규칙 참조를 검증.
9. 재현 가능한 빌드와 감사 산출물로 최종 DB를 검증.

**구조적 커버리지 100%는 의미적 완성 100%와 다르다.** 파싱 행이 존재한다고 게임 규칙을 이해한 것이 아니며, 후보 연산이 생성됐다고 실행 가능한 규칙이 된 것도 아니다.

## 3. 불변 기준과 데이터 보존 원칙

### 3.1 기준 릴리스
- `fm1-carddb-29`가 현재 기준 원본 릴리스다.
- DB29의 태그와 Release 파일은 수정·덮어쓰기·재발행하지 않는다.
- DB30은 모든 품질 게이트 통과 후 사용자 명시 승인 전까지 발행 금지.
- PR #9는 검증 완료 전 main 병합 금지.

### 3.2 원본과 해석 분리
- 원본 payload, enum 원값, 텍스트, URL, 이미지 및 체크섬을 보존한다.
- 정규화, 추론, 매뉴얼 해석, 커뮤니티 자료, OCR 결과는 원본을 대체하지 않고 별도 레코드로 연결한다.
- 원문을 수정하거나 의미가 좋아 보이도록 바꾸지 않는다.
- 카드 ID, 효과 절 ID, 원본 텍스트 범위, 상세 URL을 검토 큐에 보존한다.
- 확인되지 않은 수치·대상·발동 조건·우선순위를 추정으로 채우지 않는다.

### 3.3 상태값
- `source_verified`: 공식 원본에서 직접 확인
- `manual_verified`: 매뉴얼 문구로 확인
- `inferred`: 추론 결과이며 근거/신뢰도 필요
- `not_applicable`: 비적용임을 확인
- `source_absent_confirmed`: 원본에 값이 없음을 확인
- `pending_source_review`: 원본 근거 확인 대기
- `pending_engine_verification`: 정의는 있으나 엔진 동작 검증 대기
- `executable=false`: 후보로만 보존, 실제 게임 실행 규칙으로 사용 금지

주의:
- `unmapped=0`은 이름/enum이 카탈로그에 연결됐다는 뜻일 뿐 의미 검증 완료가 아니다.
- `unresolved cost parsing=0`은 실제 소울 지불 규칙 검증 완료가 아니다.
- 잔여량을 낮추려고 메타데이터로 오분류하거나 검토 행을 삭제하지 않는다.

## 11. Actions 운영 원칙

사용자는 불필요한 Actions 실행과 실패 반복으로 시간을 낭비하는 것을 강하게 문제 삼았다.

1. 작은 코드 수정마다 전체 DB 감사를 하지 않는다.
2. parser/test/doc 변경을 한 묶음으로 모은다.
3. PR 이벤트의 경량 회귀 테스트를 먼저 통과시킨다.
4. 실질적인 데이터 변경이 누적된 뒤 전체 `audit-release`를 1회 실행한다.
5. 전체 감사 입력은 `fm1-carddb-29`, `publish_release=false`.
6. `probe`/`crawl`은 원본 수집 문제가 있다는 증거가 있거나 사용자 요청이 있을 때만 실행한다.
7. Actions 실패 시 실패 단계와 로그를 확인하고 원인 수정 없이 재실행하지 않는다.
8. 잔여 수치가 그대로면 parser/분류 코드가 실제로 바뀌었는지, 집계가 하드코딩됐는지 확인한다.
9. 성공 여부만 보고하지 말고 실제 잔여량과 이전 기준선 대비 증감을 보고한다.

현재 feature branch workflow push trigger는 `main`과 `feat/carddb-effect-semantic-pass`로 확장되어 있다. 커밋 메시지에 `[full-db-audit]`가 있으면 DB29 전체 감사가 실행된다. #446 실행을 위해 추가한 설정이다. 이후 반복 실행 방지를 위해 브랜치 트리거 유지/제거를 검토한다.
