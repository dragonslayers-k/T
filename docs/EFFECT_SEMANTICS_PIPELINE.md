# 효과 문구 분석·실행 규칙 단계

## 왜 별도 단계인가
카드 텍스트를 DB에 저장하는 것과 게임 효과를 실제로 실행하는 것은 서로 다른 작업이다. TextBase / TextExtra는 원문 근거이며, 문장만 보고 실행 규칙을 확정하면 조건·타이밍·대상·피해 계산 순서가 왜곡될 수 있다. 따라서 현재 추출 상태를 유지하고 아래 단계를 별도 데이터로 추가한다.

## 효과 의미 스키마 제안
각 효과 단위로 다음을 기록한다.
- effect_key: 효과 분류의 안정적인 키 (예: attack.ignore_dp)
- trigger: 선언된 이벤트 (공격 선언, 공격 성공, 소환, 턴 시작/종료 등)
- actor / target: 효과 소유자와 영향을 받는 대상
- condition: 비교·상태·레벨·속성 등 전제조건의 AST
- operation: stat 변경, 직접 피해, 소울 생성, 상태 부여 등 연산
- parameters: 수치/비율/횟수; 수치는 원문에서 추출하고 단위 보존
- duration / stacking: 지속 및 중첩 규칙
- resolution_order: 엔진 처리 순서가 입증된 경우에만 지정
- source_text_id / evidence / verification_status: 출처와 검증 내역

## 처리 단계와 상태
1. extracted_unverified — 원문과 출처를 보존한 상태.
2. pattern_candidate — 표면 패턴 후보만 찾음. 실행 가능한 효과 아님.
3. manual_mapped — 매뉴얼 정의와 대응시켰으나 카드/문맥 검증 전.
4. semantics_verified — 매뉴얼·사이트 데이터·실제 게임 결과 등 증거를 연결.
5. engine_implemented — 실행 엔진에 구현됨.
6. test_verified — 회귀 테스트와 대표 사례가 통과함.

상태는 단방향 자동 승격하지 않는다. 키워드/정규식 일치만으로 semantics_verified 이상을 부여하지 않는다.

## 후보 분류 체계
- 전투 타이밍: 공격시, 공격 성공시, 방어시, 피해를 받을 때
- 능력치 변경: AP/DP/HP 증가·감소·고정·교환
- 피해 처리: DP 무시, 직접 HP 공격, 추가 피해, 반격 무효
- 상태/제어: 기술 봉쇄, 석화, 혼란, 공포, 매료 등
- 자원: LP 및 소울 획득/감소/변환
- 소환/배치: 소환 조건, 지형·유닛 상호작용
- 지속/범위: 턴, 필드, 아군/적군/특정 분류 대상
- 비게임 안내/오류 텍스트: 안내 문구와 invalid 값은 카드 효과 후보에서 제외하고 원본은 보존

## 데이터 정책
- TextBase와 TextExtra를 하나의 문자열로 합치지 않는다.
- TurnType, DurationType, Skill1, Skill2 같은 구조화 필드는 문구 기반 추론과 독립적으로 저장한다.
- 카드별 상세 URL 및 원문 텍스트 ID를 모든 효과 후보에 연결한다.
- NCS/BONUS 등의 소울 코드는 별도 코드·아이콘·검토 상태로 남기고, 확인되지 않은 규칙을 색상/속성 의미로 확정하지 않는다.
- 미지원·불명확 효과도 삭제하지 않는다. 런타임에서 지원 불가로 표시할 수 있도록 원문과 상태를 유지한다.

## 우선 검증 방식
1. 반복 등장하는 이름/문구 템플릿을 빈도순으로 묶는다.
2. 한 템플릿 안에서 수치·대상·조건이 다른 변형을 구분한다.
3. 매뉴얼 항목과 근거 URL/페이지를 연결한다.
4. 효과마다 정상 사례·경계 사례·상호작용 사례를 테스트 데이터로 만든다.
5. 효과가 겹칠 때의 해결 순서는 실제 근거가 있을 때만 작성한다.

이 문서는 구현 계약이며, 현재 DB의 효과가 이미 게임 엔진에서 실행 가능하다는 의미가 아니다.
