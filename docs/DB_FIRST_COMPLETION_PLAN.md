# FM1 카드 DB 우선 완성 — 작업 순서 및 완료 기준

작성일: 2026-11-04

## 결정

카드 DB 완성을 게임 구현보다 먼저 끝낸다. `T` 저장소를 카드 원본·정규화·검증의 단일 기준점으로 삼고, `FM-OFFLINE` 저장소는 DB 완료 게이트가 통과되기 전까지 게임 기능 확장을 중단한다. DB 변환기는 DB 검증용 소비자 테스트에 필요한 최소 수정만 허용한다.

기존 `fm1-carddb-29` 릴리스는 불변 기준선으로 보존한다. 다음 DB는 새 태그로 발행하며 기존 릴리스를 덮어쓰지 않는다.

## 원칙

1. 원본 값과 원본 URL/이미지/설명은 절대 추정값으로 덮어쓰지 않는다.
2. 모든 값에는 상태와 근거를 붙인다: `source_verified`, `manual_verified`, `inferred`, `not_applicable`, `source_absent_confirmed`. 단순 `unknown`, 빈 문자열, 누락 상태를 완료로 세지 않는다.
3. 원본에 없는 값은 매뉴얼, 카드 이미지, 카드 상세 설명, 공식 enum, 검증 가능한 보조자료, 유사 카드 순으로 조사한다. 끝내 확인되지 않더라도 게임 진행에 필요한 규칙·비용은 합리적 추정값을 채우되 반드시 `inferred`와 근거/신뢰도를 기록한다.
4. “추출됨”은 “해석·검증됨”이 아니다. 텍스트 추출, 후보 절(clause), 커뮤니티 후보를 검증 완료나 실행 규칙으로 계산하지 않는다.
5. 커뮤니티 근거와 매뉴얼 근거가 충돌하면 출처별 해석을 모두 보존하고 기본 선택 근거를 명시한다.
6. 카드별 원본 링크, 상세 링크, 이미지 원본 링크, 로컬 이미지 해시, 출처 필드 및 원문 설명을 카드 ID에 연결한다.

## 단계 A — 현재 기준선 고정 및 전수 갭 분석

- `fm1-carddb-29`와 현재 기본 브랜치의 소스/스크립트/워크플로를 기준선으로 기록한다.
- 15,350개 카드 ID와 분류별 기대 수량을 대조한다.
- 55개 원본 필드의 필드별 존재율, 값 종류, enum 해석률, 미입력 수, 미확인 수를 산출한다.
- 카드별 상세 URL·목록 URL·대형/소형 이미지 URL·이미지 파일·SHA-256·설명 원문을 대조한다.
- RequireLP/RequireSoul 비용, Skill1/Skill2, TextBase/TextExtra 효과, 인챈트/마법/아이템/지형 효과를 별도 갭 목록으로 만든다.
- 누락을 카드 ID와 필드명으로 추적할 수 있는 CSV/JSON 보고서를 만든다. 집계 숫자만으로 완료 판정하지 않는다.

## 단계 B — 카드 원본 데이터 완성

- 모든 원본 필드의 값과 의미를 확인하고 enum/분류표를 정규화한다.
- 필드별로 원본 확인, 매뉴얼 확인, 추정, 해당 없음, 원본 부재 확인 상태를 기록한다.
- 이름·분류·속성·레벨·능력치·희귀도·제한·구매/발매 정보·비용·기술 등 필드 간 모순을 탐지한다.
- 카드 이미지의 비용/기호/문구가 DB 원문과 다르면 카드별 검토 항목으로 남기고 이미지 근거를 기록한다.
- 미입력은 조사해 채운다. 원본에 값이 없는 것이 확인된 경우에만 `source_absent_confirmed`로 닫는다.

## 단계 C — 소울 비용과 카드 기술 완성

- 15,350장 전체의 RequireLP/RequireSoul을 토큰 단위로 해석한다.
- 하이브리드 소울, NCS, BONUS 등 특수 비용은 원본 토큰을 보존하고, 확인/추정한 지불 규칙을 구조화한다.
- 비용을 빈 값이나 0으로 대체해 미확인을 숨기지 않는다.
- Skill1/Skill2의 모든 사용 enum과 카드별 연결을 빠짐없이 정리한다.
- Manual.zip의 27개 기본 기술을 우선 확정하고, 후대 확장 기술은 별도 출처/충돌/추정 상태를 기록한다.
- 카드 효과(TextBase/TextExtra)는 모든 절을 카드별 구조화 데이터로 만들고, 발동 시점·대상·조건·수치·지속시간·중첩/상쇄·예외를 채운다.
- 확인 근거가 부족한 효과도 사용자 요구에 따라 실행 가능한 추정 규칙을 부여하되, `inferred` 상태와 신뢰도·근거·추정 이유를 남긴다. 원문을 바꾸지 않는다.

## 단계 D — DB 자체 품질 게이트

다음 조건을 모두 만족하기 전에는 새 릴리스를 발행하지 않는다.

- 카드 수 15,350, 분류별 수량 일치, 중복 ID 0.
- 모든 카드의 필수 원본 식별자/URL 및 이미지 참조가 카드 ID에 연결됨.
- 30,700개 이미지의 파일/아카이브/해시 검증 완료.
- SQLite integrity 및 foreign-key 오류 0.
- 55개 필드 전체에 필드별 상태·누락·미확인 보고서가 있고, 설명되지 않은 공백 0.
- 모든 비용 토큰이 해석 또는 명시적 추정되며, 미해결 토큰 0.
- Skill1/Skill2 원본 행이 모두 매핑되거나 명시적 무기술/해당 없음으로 분류되고, 미분류 enum 0.
- 모든 효과 원문이 절 단위로 연결되고, 모든 절이 확인 규칙 또는 추정 규칙에 연결되며, 미분류 절 0.
- 카드별 데이터 완전성 및 근거/추정 상태를 조회할 수 있는 최종 감사 보고서 생성.
- 자동 테스트와 표본 수동 대조를 통과. 표본은 각 카드 분류, 비용 유형, 기술 유형, 효과 유형을 포함한다.

## 단계 E — 불변 DB 릴리스

- 위 게이트 통과 후에만 새 버전 태그(예: `fm1-carddb-30`)와 체크섬/요약/갭 보고서/SQLite/이미지 아카이브를 함께 발행한다.
- 릴리스 태그는 불변으로 취급한다.
- 실패 시 새 태그를 발행하지 않고 실패 원인과 영향을 받는 카드 ID/필드를 보고한다.

## 단계 F — 게임 구현 재개

DB 릴리스가 승인된 뒤에만 FM-OFFLINE을 해당 태그로 고정한다. 이후 게임은 DB 내용을 임의 재해석하지 않고 DB의 정규화 규칙과 provenance를 사용한다. 전투 엔진은 DB 규칙 ID를 구현하고, 카드별 회귀 테스트 및 Android 에뮬레이터 테스트를 진행한다.

## 작업 통제

- DB 단계가 끝나기 전 게임 규칙/화면/전투 기능 변경 금지.
- 각 커밋 전 로컬/CI 사전 검증, 변경 파일 및 영향 범위 확인.
- 실패한 워크플로를 원인 규명 없이 재실행하거나 새 커밋으로 덮지 않는다.
- 보고 시 반드시 완료/미완료, 수량, 실패한 검증, 실제 산출물 링크를 구분한다.
- “성공”은 해당 게이트만 통과했다는 뜻으로 제한하며 전체 DB 완성 또는 게임 완성을 과장하지 않는다.
