# 카드 DB 전수 갭 조사 — DB29 기준선

## 목적과 적용 범위

이 문서는 불변 릴리스 `fm1-carddb-29`를 입력으로 삼아, DB 자체의 누락·미입력·미확인 항목을 카드별로 조사하기 위한 기준이다. 이 단계는 게임 구현이 아니라 DB의 사실관계와 완전성 조사다.

## 데이터 보존 및 상태 구분

- 원본 카드 레코드, 원본 enum, 원본 텍스트, 원본 URL, 원본 이미지와 체크섬은 변경하지 않는다.
- 정규화 결과, 매뉴얼 해석, 카드 이미지 판독, 보조자료, 추정치는 원본과 분리된 별도 필드/테이블에 둔다.
- 각 값의 상태는 `source_verified`, `manual_verified`, `inferred`, `not_applicable`, `source_absent_confirmed`로 구분한다.
- 추출만 된 텍스트나 후보 규칙은 확인된 해석으로 간주하지 않는다.
- 추정값은 출처, 근거, 추정 방법, 신뢰도를 보존한다. 미확인을 0, 빈 값, 일반 규칙으로 은폐하지 않는다.
- 매뉴얼과 후대 커뮤니티 자료가 충돌하면 각각의 해석을 분리하고 기본값 선정 근거를 기록한다.

## 1차 전수 감사 항목

1. 15,350개 카드 ID, 분류별 기대 수량, 중복/누락, 카드명, 목록 URL, 상세 URL.
2. 원본 필드 55종의 카드별 존재 여부, 빈 값 수, enum 해석 여부, 정규화 오류 및 필드 간 모순.
3. 30,700개 대형/소형 이미지의 원본 URL, 카드 ID 연결, 실제 파일, 형식, 크기, SHA-256, 아카이브 무결성.
4. RequireLP와 RequireSoul의 카드별 원문/토큰/비용 해석/미해결 상태. 하이브리드, NCS, BONUS 및 텍스트형 비용 포함.
5. Skill1/Skill2 원본 enum의 전체 사용 목록, 카드별 연결, 미매핑 enum과 별칭 후보.
6. TextBase/TextExtra 원문 및 절 단위 효과 후보의 카드별 연결, 구조화 상태, 미해석 문장 목록.
7. 마법/인챈트/아이템/지형별 고유 필드 및 효과 구조화 공백.
8. SQLite integrity, foreign-key integrity, FTS 검색, 정규화 테이블 간 참조 무결성.

## 산출물

- `data/audit-report.json`: 전수 집계 및 완료 게이트.
- `data/card-field-gap-report.csv`: 카드 ID × 필드별 누락/빈 값/미확인 상태.
- `data/card-field-gap-report.jsonl`: 동일 항목의 기계 판독 상세 근거.
- 비용·기술·효과별 개별 갭 CSV/JSONL.
- 이미지 누락/해시 오류 목록.
- 표본 수동 대조 목록 및 결과.

집계만 출력하고 카드 ID별 상세를 생략하지 않는다. 대규모 보고서는 Actions artifact로 보관한다.

## 완료 판정

이 감사 실행 자체는 현황 파악 단계이며, DB29가 완전하다고 미리 가정하지 않는다. 발견된 갭은 보완 작업 목록으로 분리한다. 새 불변 DB 릴리스는 카드별 갭이 모두 닫히고, 추정 상태까지 근거와 함께 기록되며, 자동 검사 및 표본 수동 대조가 통과한 뒤에만 발행한다.

## 금지 사항

- DB29 릴리스 자산이나 태그를 덮어쓰지 않는다.
- 이 감사 단계에서 FM-OFFLINE 게임 코드/전투 규칙을 수정하지 않는다.
- 텍스트 추출 수량을 구현 완료 수량으로 보고하지 않는다.
- 미확인/미입력/미해결 건수를 0으로 임의 설정하지 않는다.


## 자동 전수 갭 보고서

현재 기본 브랜치에는 카드별 55개 원본 필드 매트릭스와 비용·기술·효과별 JSONL 검토 대기열을 생성하는 `scripts/build_gap_reports.py`가 추가되었다. 전체 감사 워크플로에서 생성하며 Actions artifact로 보관한다. 원본 스냅샷 무결성과 의미/규칙 완전성은 서로 다른 게이트로 판정한다.

갭 보고서 생성기의 문법 검증 오류를 수정했으며, 다음 전수 감사 실행에서 전체 보고서 생성과 산출물 업로드까지 확인한다.

## 2차 의미 보완 파이프라인

- `scripts/infer_unmapped_skills.py`: 매뉴얼/커뮤니티 규칙에 연결되지 않은 Skill1/Skill2 enum 917종을 다시 조사한다. 해당 기술을 실제로 가진 카드의 TextBase/TextExtra에서 기술명으로 시작하는 설명 블록을 찾고, 카드 ID·상세 URL·원문·변형 수를 근거로 저장한다.
- 직접 설명 근거가 있는 기술은 `inferred` / medium 신뢰도로, 카드 설명에 대응 문장이 없는 기술은 `inferred` / low 신뢰도로 별도 저장한다. 두 경우 모두 원본 enum은 그대로 보존하고 기본 실행 가능 상태로 가장하지 않는다.
- `scripts/infer_effect_interpretations.py`: 분리된 48,281개 효과 절 전체에 발동 시점, 주체, 대상, 조건, 수치, 조작 후보를 추출한 구조화 해석을 저장한다. 인식되지 않는 문장도 원문을 보존한 low-confidence 해석으로 남겨 빈칸으로 버리지 않는다.
- `card_effect_interpretations`는 원본 `card_effects` 및 `card_effect_clauses`와 별도 테이블이며, 원문·카드 상세 URL·해석 방법·신뢰도를 함께 보관한다.
- CI는 원본 무결성 외에 기술 미매핑 0건, 카드별 기술 연결 100%, 효과 절 해석 누락 0건, 외래키 오류 0건을 별도 확인한다. low-confidence 건수는 별도로 보고해 수동 검증 대상이 사라진 것처럼 표시하지 않는다.

## 추론 결과 해석 원칙

기술명과 설명 문장을 연결한 것은 DB 공백을 메우는 1차 추론이며, 모든 규칙이 엔진 테스트까지 통과했다는 의미는 아니다. 특히 243개 기술은 카드 설명에서 기술명에 대응하는 설명 블록을 찾지 못했으므로 low-confidence name-only inference로 표시된다. 이들은 원문 근거를 추가 탐색하고 카드별 상세 URL을 통해 보강해야 한다. 효과 해석도 패턴 추출 결과를 AST 후보로 저장한 상태이며, 복합 조건·순서·대상 선택·지속시간은 별도 규칙 검증 대상이다.

## 공식 매뉴얼 원문 재확인 및 27개 기본기술 교정

Dropbox의 실제 `/판마/Manual.zip` (rev `65f348bcc93d60972fdd5`, 2026-11-01 수정)을 다시 열어 `specialability.htm`의 `특수기술목록표`를 추출했다. 원문 추출본은 `data/rules/manual-specialability-source.txt`에 보존했다. 27개 기본 규칙 정의를 이 원문에 맞춰 교정했다. 특히 돌진공격의 AP=0 예외, 재생능력의 무피해 발동, 용맹/공포의 AP=0 추가 피해, 매료공격의 DP 방어 조건, 방패파괴의 음수 DP 예외, 공격복제의 상대 유효 AP 사용 등을 명시했다.

2017 커뮤니티 기술 목록은 매뉴얼과 별도 출처로 유지한다. 카드 설명에서 근거를 못 찾은 저신뢰 기술은 이 목록과 대조하여 community_documented_candidate로 승격하되, 원문 매뉴얼과 같은 권위로 취급하지 않는다.

## 3차 전수 보고서 보정

55개 필드의 부재는 카드 종류별 실제 사용 여부를 기준으로 `not_applicable`과 `missing_on_card`를 구분한다. 소울 비용 831건의 하이브리드/NCS/BONUS 추론은 미해결 공백으로 세지 않고, 원본 토큰과 추론 상태를 카드별로 함께 내보낸다. 실제 미해결 비용은 별도 0건 게이트로 확인한다.

## 4차 보완: 카드 원문 표기 변형과 누락 필드 구분

기술 설명 추출에서 원문 블록 앞의 `★/☆/▶/※/◈` 표식을 제거한 뒤 기술명을 대조하도록 수정했다. `네이처드레인/네이쳐드레인`, `기계배치/기체배치`, `다잉메시지/다잉메세지`처럼 실제 카드 설명에서 확인된 표기 변형도 별칭 근거로 연결한다. 기존 low-confidence 기술을 새 DB 빌드 때 다시 조사해, 이전의 name-only 추정을 카드 원문 근거로 승격할 수 있게 했다.

카드별 55개 필드 매트릭스에서 `TextExtra`의 빈 문자열은 원본에 추가 설명이 없음을 뜻하므로 `source_absent_confirmed`로 구분한다. 카드 종류에 적용되지 않는 필드는 `not_applicable`로 구분한다. CI는 적용 가능한 필드 누락, 미확인 비용, 미매핑 기술이 남으면 실패하도록 강화했다.

CI 스크립트에서 매뉴얼 원문 파일을 명령 인자로 잘못 붙인 경로 오류를 수정했다. 원문 파일은 Actions 산출물에만 포함하며 DB 빌드 명령으로 실행하지 않는다. 전체 감사 재실행으로 확인한다.

## 5차 잔여 저신뢰 기술의 처리

원문 표기 변형을 반영한 재검사로 카드 설명 근거가 확인되는 기술을 추가 승격한다. 설명이 실제로 없는 기술은 빈 규칙으로 남기지 않고, 기술명에서 추론 가능한 상위 범주(속성 아레아/필드 오라, 펌프킨 계열, 눈덩이 계열, 묘지 상호작용, 코스트 감소, 소환 상호작용, 트랩/구조물 등)를 `nameBasedGuess`로 저장한다. 단, 수치·대상·발동 조건을 확인할 근거가 없으므로 `executable=false`, low confidence로 유지한다. 이는 데이터 누락이 아니라 원본 근거 부재를 명시한 추론 레코드다.

## 6차 효과 절 분류 보정

효과 절이 단독 기술명만 담고 있는 경우에는 해당 기술을 `game_rule_catalog`와 연결하는 `linked_rule_reference`로 분류한다. 랭크 카드 안내/FAQ, invalid, 참고문구는 효과 규칙으로 오인하지 않고 비효과 참고자료로 구분한다. 실제 효과 문장에 대해서는 AP/DP/HP, 피해·파괴, 회복, 드로우, 소환, 상태/기술 부여·해제, 자원 변경, 이동, 장착 등의 공통 연산 후보를 추출한다.

## 7차 비효과 문구와 실제 미해석 효과 분리

랭크 카드 안내/FAQ, invalid, 빈 구분 절은 해석 신뢰도 low로 집계하지 않고 `not_applicable`로 분리한다. 단독 기술명은 카탈로그 규칙 참조로 연결한다. 실제 효과 문장 중 패턴으로 동작을 식별하지 못한 문장만 low-confidence queue에 남긴다.


## 다음 재검증

갭 보고서 생성기의 줄바꿈 문법 오류를 수정했다. 다음 DB29 재실행에서는 전수 원본·이미지·SQLite 감사와 함께 효과 저신뢰 문장, 추론 기술, 비용 추론 대기열을 별도 소형 Actions artifact로 업로드해 잔여 건을 직접 검토하고 보완한다.


## 추론 매핑 원자성 수정

미매핑 기술은 이제 추론 규칙을 `game_rule_catalog`에 먼저 INSERT/UPSERT한 다음, `card_rule_mappings`와 `skill_enum_inventory`의 실제 `rule_id`를 연결한다. 처리 건수만 증가하고 DB 매핑이 그대로 남는 회귀를 막기 위해 신규 규칙 레코드, 카드별 연결 수, enum inventory 상태를 검사하는 SQLite 단위 테스트를 추가했다. 다음 단계는 15,350장 원본 DB를 새 코드로 다시 생성하고 효과 해석 잔여치를 재검증하는 것이다.


## 8차 기술·효과 의미 보완 및 외부 정의 재대조

- DB29 원본 기반 실행 #130에서 Skill1/Skill2 enum 917종을 전부 규칙 카탈로그에 연결했고, 카드별 기술 행 20,762건 중 4,043건은 추론 규칙에 연결했다. 원문 카드 설명 근거가 확인된 기술 884종, 후대 커뮤니티 정의가 추가 확인된 기술 9종, 여전히 명칭 기반 저신뢰로 남은 기술 24종을 분리해 보존한다.
- 2017-01-30 인벤 게시물의 실제 본문에는 13시의저주, 가치감정 등 다수 특수기술의 구체 발동 조건과 수치가 카드별 규칙과 함께 기록되어 있다. 이 자료는 매뉴얼보다 낮은 권위의 community reference로 연결하며 기본 실행 규칙으로 승격하지 않는다.
- 커뮤니티 기술 추출기는 동일 줄 기술명: 설명뿐 아니라 기술명과 콜론/설명이 다음 줄로 분리된 문장도 읽도록 보완했다. 잔여 저신뢰 기술은 대표 카드 ID·상세 URL·TextBase/TextExtra 원문을 최대 3장까지 감사 결과에 출력해 추가 교차검증한다.
- 효과 절 48,281건은 모두 해석 레코드를 보유하나 #130 기준 저신뢰 5,015건이 남았다. AP/DP/HP 복합 선택(최고/최저 수치), 일반 한국어 동작 어휘(부여·제거·변경·교환·무효화·이동·자원 변경 등), 제목과 설명 사이 콜론 분리 문형을 추가 구조화한다. 해석은 executable=false와 원문 보존을 유지하고 자동 실행 규칙으로 오인하지 않는다.
- effect-low-confidence-summary.json은 저신뢰 행 수, 중복 문장 수, 해석 분류별 건수, 반복·희귀 문장 및 카드 상세 URL을 제공한다. 이 산출물을 다음 전수 실행에서 확인해 남은 문형별 규칙을 추가한다.

## 카드 종류별 필드 적용성 후보 구분

카드별 필드 매트릭스는 원본 payload 부재와 카드 종류별 적용성 후보를 구분한다. 동일 카드 종류의 다른 카드에서 한 번도 나타나지 않는 필드는 `not_applicable_candidate`로 표시한다. 이는 유형별 관측에 따른 후보일 뿐 원본 스키마의 공식 확정이 아니므로, 원본 문서/실제 카드 표본으로 확인되기 전까지 `not_applicable`로 승격하지 않는다. 동일 종류에서 관측된 필드가 특정 카드 payload에 없으면 `source_absent_confirmed`, payload에는 있으나 정규화 테이블에 없으면 `missing_on_card`로 유지한다.


## 10차 카드 페이지 근거 확인 및 참조절 연결

- 카드 설명 앞의 ◇/◆/※ 등 시각 표식은 분석용 문자열에서만 제거하고 원본 `rawText`에는 그대로 보존한다. 기술명 단독 절은 기술 카탈로그 참조로 연결한다.
- 카드명 단독 절과 `카드명 : 카드명` 형식은 카드 DB의 실제 카드명/ID와 대조해 비효과 카드 참조로 연결한다. 이름이 일치하지 않으면 미확인 효과로 유지한다.
- 이름만으로 추정된 24개 기술은 공식 카드 상세 페이지를 별도 조회해 원문 근거를 수집한다. 조회 결과는 증거 산출물이며, 그 자체로 기술 의미나 실행 가능성을 확정하지 않는다.
- 카드 종류별 필드 적용성은 같은 카드 종류에서 관측된 필드 집합을 기준으로 `not_applicable_candidate`를 별도 표시한다. 유형별 표본이 없는 상태를 공식 `not_applicable`로 승격하지 않는다.


## 소울 비용 토큰의 근거 등급과 미확정 의미

- 토큰 코드 `81`은 중립 무소울, `82`는 NCS, `83`은 BONUS로 서로 다른 정체성을 유지한다. 파서가 토큰을 읽었다는 것은 토큰 식별에 성공했다는 뜻이지, 해당 자원을 실제로 어떤 소울로 지불할 수 있는지까지 검증했다는 뜻은 아니다.
- 하이브리드 코드는 두 색상 조합을 보존하지만, 양쪽 색상을 모두 요구하는지 또는 어느 한쪽으로 대체 지불할 수 있는지는 독립적인 기준 카드/실험 근거가 없어 `mapping_review`로 남긴다.
- 2025-08-10 DCInside의 데메 시즌 24 카드 리뷰는 `탈영혹은귀환`의 판마 원본 비용을 NCS 소울로 언급하면서, 획득 유닛의 `무소울화`가 무속성화인지 실제 무소울 비용 처리인지 불명확하다고 적고 있다. 이는 NCS가 일반 중립과 동일하다고 단정할 수 없다는 커뮤니티 관찰 근거지만, 원작 판마의 공식 지불 규칙을 확정하는 자료는 아니다.
- BONUS의 지불 규칙을 직접 확인하는 공식 매뉴얼/독립 실험 근거는 현재 확보되지 않았다. NCS와 BONUS 모두 원본 토큰을 보존하고, 서로 또는 neutral로 합치지 않으며, 결제 규칙 검증 전까지 플레이 가능 판정에서 제외한다.
- 따라서 현재 `soul_cost_fully_parsed=15,350`은 토큰 문자열 파싱 완전성 지표다. 비용 지불 의미 검증 완료 지표로 표현하지 않는다. `mapping_review=52`, `semantic_review=779`는 별도 완료 조건으로 유지한다.


## 원본 키 부재·null·빈 문자열 분리

카드 필드 매트릭스에서 원본 키 자체가 없는 경우(`source_absent_confirmed`), 키는 있으나 JSON null인 경우(`source_null_confirmed`), 키는 있으나 빈 문자열인 경우(`source_empty_confirmed`)를 구분한다. 원본에 키와 값이 있으나 정규화 행이 없는 경우만 `missing_on_card`로 처리한다. 이 세 상태는 서로 대체하거나 0/기본값으로 보정하지 않는다.
